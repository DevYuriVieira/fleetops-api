# ADR-001 — Transactional Outbox Pattern for Relational State and Event Publication Atomicity

## Status
Accepted

## Context
In a distributed event-driven architecture, business operations frequently require updating relational state (e.g., scheduling maintenance or updating vehicle mileage) while concurrently notifying downstream systems via asynchronous messaging. 

In FleetOps API, PostgreSQL serves as the relational database and RabbitMQ serves as the message broker.

## Problem
A core architectural challenge is the **Dual-Write Hazard**. When an application attempts to write to a relational database and publish to a message broker in the same business flow, it faces an unresolvable coordination problem without distributed transactions:
1. If the database transaction commits first and the message publication fails (due to broker downtime or network partition), the event is permanently lost, leaving downstream consumers desynchronized.
2. If the message is published first and the database transaction fails (due to constraint violations, deadlocks, or crashes), the downstream consumer processes an event corresponding to business state that never existed.

Two-Phase Commit (2PC) / XA distributed transactions are not supported by modern cloud-native message brokers like RabbitMQ, introduce high latency, and create catastrophic availability bottlenecks.

## Decision
We adopt the **Transactional Outbox Pattern** implemented directly within `FleetOpsDbContext.SaveChangesAsync`:
1. Domain events generated by aggregate roots during command execution are captured by the Entity Framework Core change tracker.
2. For each domain event, an `OutboxMessage` entity is instantiated and added to the `DbSet<OutboxMessage>` within the active database transaction.
3. Both domain state mutations and outbox records commit atomically within the relational boundary of PostgreSQL.
4. An asynchronous worker (`OutboxProcessor` running `OutboxService`) polls pending messages from `outbox_messages`, publishes them to RabbitMQ with Publisher Confirms, and marks them as processed upon confirmation.

## Alternatives Considered
1. **Direct Publish After Commit:** Commit database transaction, then immediately invoke `channel.BasicPublishAsync`.
   - *Rejection:* Vulnerable to permanent event loss if the process crashes or network fails between the commit and publish.
2. **Direct Publish Before Commit:** Publish to RabbitMQ, then commit the database transaction.
   - *Rejection:* Vulnerable to phantom event processing if the database commit fails.
3. **Two-Phase Commit (2PC / XA):** Coordinate PostgreSQL and RabbitMQ via distributed transaction coordinator.
   - *Rejection:* High latency, complex operational overhead, and RabbitMQ does not support XA transactions.
4. **Change Data Capture (CDC / Debezium):** Tail PostgreSQL write-ahead log (WAL) to extract outbox events.
   - *Rejection:* Introduces additional infrastructure runtime (Kafka Connect, ZooKeeper/Kafka), increasing operational burden beyond the requirements of the verified problem scope.

## Why This Decision
- Guarantees that an outbox record is persisted if and only if the business aggregate mutation commits.
- Decouples API command ingestion latency from RabbitMQ availability; commands succeed even if the broker is temporarily unreachable.
- Eliminates dual-write hazards using standard relational ACID guarantees.

## Trade-offs
- **Storage Overhead:** Requires a dedicated relational table (`outbox_messages`) and periodic cleanup/archival of processed records.
- **Asynchronous Latency:** Downstream consumers receive events with polling delay (typically sub-second) rather than instantaneous delivery.
- **Redelivery Potential:** If the worker publishes to RabbitMQ successfully but crashes before updating `processed_on_utc` in PostgreSQL, the message will be republished upon worker restart, necessitating idempotent consumers.

## Consequences
- The API boundary guarantees atomic relational persistence.
- Downstream consumers must implement idempotency mechanisms.
- Event publishing semantics become **Bounded At-Least-Once**.

## Risks
- Outbox table growth if RabbitMQ suffers prolonged outages. Mitigated by bounded polling, database indexing, and operational monitoring.

## Operational Impact
- Requires monitoring pending messages count (`processed_on_utc IS NULL`) and failed attempts (`attempts >= maxAttempts`).

## Future Evolution
- If event throughput exceeds thousands of messages per second, CDC via PostgreSQL logical decoding (`test_decoding` or Debezium) can be evaluated to eliminate database polling overhead.
